# 性能测量与发布前检查

## 2026-10-17：发布前性能测试

已测场景未发现持续高占用、崩溃或 Metal command 错误；**尚不能标记为完整性能验收通过**。原生界面自动化连接中断，窗口隐藏／最小化／关闭等实际场景未完成；CPU/GPU 总功耗和完整泄漏扫描也受测量权限限制。以下严格区分真实窗口、组件压力测试和未测项目。

### 条件与方法

- 构建基线：`f820e7e`，加本次尚未提交的可选性能采样入口。SwiftPM Release 可执行文件、独立本地签名测试 bundle；Xcode Release 另行构建通过。
- 机器：MacBook Pro，Apple M5 Pro，15 核 CPU、48 GB 内存；macOS 26.5，arm64，电池供电，低电量模式关闭。其他桌面应用仍在运行，未将其关闭或将机器视为受控实验环境。
- 真实资料库副本：164 首音频（162 FLAC、2 MP3）、307 条已导入歌词、2 个列表、186 个列表条目、169 次会话和 2865 个收听片段。源库只读在线备份，测试写入独立副本，偏好使用独立 bundle ID，原始音频不修改。
- 实际播放经过 AVAudioEngine 和源 PCM 分析，mixer 输出静音。画面使用真实 SwiftUI 与 Metal，主窗口 1140×760 pt、2× backing scale；水族箱窗口 drawable 为 1204×778，全屏为 2560×1607 像素。
- 进程计数每秒读取一次，CPU 的 Mach ticks 转换为纳秒；**CPU 100% 表示占满一个核**。内存使用 physical footprint（含压缩归属），不以虚拟地址空间或单纯 RSS 判断应用实际占用。
- 稳态排除各阶段前 10 秒、状态快照超过 3 秒的数据和已标记的切换／诊断阶段；初始空闲与纯播放按运行状态另行过滤。未移除单个 CPU 异常值。采样有效性及原始数据可复核。
- 仪器自身有开销：50 ms 主线程心跳、1 Hz JSON 快照、Metal command 完成回调、外部 1 Hz libproc 采样。CPU、唤醒和写盘数字包含这些开销，不等于完全无仪器的正式包数字。

水族箱默认窗口的 GPU 单帧平均 1.08 ms，全屏平均 2.77 ms。这里的帧率是 command 完成率，不是屏幕呈现率；频谱 Canvas 与 WindowServer 合成不在该 GPU 时间中。

### 40 条鱼与省电配置：组件压力测试

原生 UI 连接中断后，通过同一 `TankRenderer` 的 simulation、shadow pass 与主 pass 绘制到可复用离屏纹理，无像素回读。每场景预热 30 帧、记录 120 帧，按目标帧率节拍运行。此测试验证渲染容量，**不是 40 条鱼完整应用的 CPU／耗电测试**；当时真实窗口仍在后台共同使用 GPU，不能作为独占 GPU 的硬件基准。

| 场景 | 分辨率 | CPU 模拟＋编码均值／P95 | GPU 均值／P95 | Metal 错误 |
|---|---:|---:|---:|---:|
| 默认 8 鱼＋3 水母，窗口 | 1204×778 | 1.38／2.39 ms | 1.32／2.29 ms | 0 |
| 默认 8 鱼＋3 水母，全屏 | 2560×1607 | 1.45／2.80 ms | 2.99／4.27 ms | 0 |
| 28 鱼种＋3 水母，全屏 | 2560×1607 | 3.63／4.54 ms | 3.20／4.32 ms | 0 |
| 40 鱼＋5 水母，标准 30 fps | 2560×1607 | 4.72／5.92 ms | 3.71／5.18 ms | 0 |
| 40 鱼＋5 水母，省电 24 fps | 1280×804 | 4.80／5.99 ms | 1.72／2.29 ms | 0 |
| 仅场景，无鱼／水母 | 2560×1607 | 0.21／0.37 ms | 2.29／3.53 ms | 0 |

标准配置阴影 2048²，省电配置阴影 1024²。省电配置减少每帧 GPU 工作量并降低目标帧率，但这些耗时不能直接换算成电池续航。初始化耗时约 175～348 ms，包含资源与模拟构建，不代表首次安装后冷磁盘启动。

### 持续运行、音频与内存

- 真实测试进程连续记录 25.3 分钟、共 1513 份状态样本，其中水族箱运行约 15.4 分钟，包含自然切歌、全屏往返和组件测试产生的共享机器负载。
- 未记录应用错误或 Metal command 错误；thermal state 全程为 nominal（0），没有超过 3 秒的过期状态快照。它们不能替代声音监听、音频设备中断或实际输入延迟验证。
- 全程采样最高 footprint 为 320.4 MiB；内核记录的生命周期瞬时峰值为 365.4 MiB，包含加载、切换和诊断工具访问。最后 5 分钟的采样范围为 286.4～289.8 MiB，没有观察到持续快速增长；不据此宣称无内存泄漏。
- 独立音频组件对真实 FLAC／MP3 交替执行 80 轮加载、播放、seek、暂停与停止，均通过。加载并播放耗时中位数 19.8 ms、P95 20.9 ms；每 10 轮采样，组件测试进程 footprint 从约 26.0 MiB 到 21.8 MiB。它不是整个 UI 应用的内存。
- 回归测试共 73 项，69 项通过、4 项 opt-in 性能测试默认跳过；这 4 项已分别显式执行并通过。真实音乐库扫描及 162 首 FLAC 的实际 PCM 解码检查通过。Xcode Release 构建通过。

### 歌词、统计与音乐库规模

- 307 条歌词加载并解析缓存约 40.2 ms。161 份真实本地歌词首次批量导入约 453.4 ms，160 份自动关联、1 份待关联；已有资料库的重复导入约 448.9 ms，覆盖模式重导入约 454.9 ms。这两次重导入正文未改变，并非实际替换 161 份旧记录的速度保证。
- 总统计、年度足迹、单曲详情三组查询合计：30 轮中位数 0.92 ms、P95 1.21 ms；针对当前实际历史规模，未验证多年百万条片段的数据集。
- 元数据规模测试如下：164 条使用实际曲目；1000～10000 条复制真实元数据用于筛选和排序，不生成或扫描同等数量的真实音频文件，也不包含 List 布局／绘制。

| 条目数 | 首次名称排序 | 已缓存连续读取 100 次 | 搜索「晴天」 |
|---:|---:|---:|---:|
| 164 | 3.03 ms | 0.022 ms | 0.40 ms |
| 1000 | 28.73 ms | 0.023 ms | 2.21 ms |
| 5000 | 118.59 ms | 0.022 ms | 10.51 ms |
| 10000 | 246.91 ms | 0.022 ms | 21.11 ms |

**需关注的性能边界**：`AppModel.visibleTracks` 在 MainActor 上执行筛选／自然排序。当前 164 首音乐库成本约 3 ms；5000 条约 119 ms、10000 条约 247 ms，缓存失效后的首次读取会占用主线程。缓存命中不重复排序，但大库首次加载、名称模式或排序条件变化值得改为后台生成结果。本轮只记录问题，没有变更排序架构。

既有导航离屏基准复测 6 次：布局中位数 137.2 ms，切换＋整张软件绘制中位数 214.4 ms；每次读取可见歌曲 4 次、完整重建 0 次。它不是鼠标点击到屏幕显示的延迟。

### 耗电及测量限制

- libproc 提供非零的 `rusage_info_v6.ri_energy_nj`。原始增量及折算值已保留，但计数覆盖范围和校准未经独立验证，不能视为应用总功耗，更不能与真实 GPU 总功耗混同。
- `powermetrics` 当前需要管理员密码，未能运行 CPU/GPU 子系统功耗采集；没有修改系统权限。Xcode 的 Power Profiler 模板实际返回“不支持 macOS，仅支持 iOS/iPadOS”，不能以一个已生成的 trace 目录宣称耗电已测成功。
- `leaks` 对本地签名进程提示不可完整调试，仅能检查受限制的只读内存；本次输出不用于判断泄漏存在或不存在。未更改正式 app 的调试权限或降低系统安全设置。
- 机器还有其他应用与屏幕负载，因此没有把电池电流、剩余时间或电量下降直接归因于 Little Ears；也未给出未经受控测试的续航小时数。

### 正式打包前仍需补测

1. 恢复原生 UI 自动化连接后，实测关闭频谱、暂停、统计／列表页面、隐藏／最小化／关闭窗口、气泡环境音、40 鱼＋5 水母的完整窗口及省电模式。现有生命周期单元测试通过，不等于这些实际 CPU／GPU／音频行为已验收。
2. 在有权限的环境执行 `powermetrics`，控制屏幕亮度、背景负载和供电条件，分别比较标准与省电模式；补齐完整可调试构建的 Allocations／Leaks 与更长时间内存观察。
3. 补做系统睡眠／唤醒、音频设备切换和真实非静音播放的中断检查。当前机器结果不能直接代表 M1 等较早芯片的表现。

所以本轮结论是：**已测的 164 首库与默认水族箱资源占用可控，大库首次排序有明确优化空间；完整发布性能验收仍待上述项目完成。**

## 历史导航延迟排查与修复

## 复现与原因

Release 构建，在独立内存数据库导入 jay 的 164 首真实歌曲，不启动播放。使用同一 1140×730 SwiftUI / AppKit 窗口，连续 6 次从正在播放切换到音乐库，并完成离屏绘制。

原实现的 visibleTracks 每次访问都筛选并做自然语言排序，音乐库每行的右键菜单又重复读取整批已选歌曲。一次切换触发 670 次完整筛选／排序，主线程因此阻塞。切换不需要重新读取音乐文件或请求网络。

## 改动

- 音乐库一次视图更新只取一份可见歌曲与选中歌曲快照，行菜单复用快照。
- 可见歌曲结果按输入变化失效：歌曲更新、搜索、目录、包含子目录和排序条件变化后才重新计算；导航、播放进度和相同筛选值不使缓存失效。
- 页面只挂载当前视图；透明保留原生 List 的方案已撤回，避免隐藏页面参与窗口交互。
- 播放位置由独立 ObservableObject 发布，进度控件单独订阅；四次／秒的进度更新不再广播到整个 AppModel。

## 测量结果

| 项目 | 修复前 | 修复后 |
|---|---:|---:|
| 切换 + 整张离屏绘制，中位数 | 909.9 ms | 268.4 ms |
| 每次切换可见歌曲读取次数 | 670 | 4 |
| 每次切换完整筛选／排序次数 | 670 | 0（复用已有结果） |
| 修复后切换布局耗时 | 未单独记录 | 81.3–144.1 ms |

撤回隐藏页面复用后，整体基准耗时下降 70.5%。之前记录的 191.4 ms 属于已撤回方案，不能作为当前版本结果。这是一组本机离屏基准，包含整张画面的软件绘制，不等同于屏幕上的输入到显示延迟，也不代表所有规模音乐库的保证值。

复测命令：

```sh
swift build -c release
.build/release/LittleEars --measure-navigation /path/to/music
```

测量仅使用内存数据库，不修改用户音乐库、列表与历史；输出 6 次样本、可见歌曲读取／重建次数和布局耗时。

## 验证

21 项测试通过，包括新加的缓存失效和播放进度隔离回归；原有真实 FLAC、播放、暂停、seek、重启恢复、统计与播放列表测试保持通过。实机已重启新版并核对 jay 的 164 首音频、两个原播放列表与原暂停位置；验证统计 → 音乐库导航、进度单独更新后时间显示仍正常，并恢复原位置。离屏检查确认其他页面没有被保留的音乐库覆盖。鼠标拖拽与完整键盘遍历没有在此轮逐项重验。

## 点击命中复查

用户报告无响应／点到别的内容后，撤回透明保留音乐库的方案。导航、播放列表和目录按钮为 plain 样式，现显式声明整行 contentShape，补齐文字之外的点击区域。背景、边缘和高光绘制不参与命中；按钮悬停状态移入独立 View，避免状态附着于共享样式。

最终版本通过工具验证了正在播放 → 音乐库导航，以及保存队列菜单打开／关闭。鼠标坐标调用出现窗口不可用错误，原生排序及右键菜单的自动化调用未能稳定验证；不能据此声称所有物理点击场景已验收，也未将透明列表认定为已实证的唯一根因。
